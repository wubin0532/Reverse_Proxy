## F1：正常新增站点导致白屏

位置：`internal/webproxy/api.go:313`、`web/src/views/WebService.vue:125`、`web/src/views/WebService.vue:657`。

`redactSites` 使用 `append([]config.SubRule(nil), sites[si].Rules...)` 复制规则。即使保存的是空数组，也会得到 nil 切片，API 随后返回 `"rules":null`。前端将响应直接赋给 `sites`，模板的 `activeSite.rules.length` 抛出 `TypeError: Cannot read properties of null (reading 'length')`，整个 Web 服务内容区无法渲染。

复现：在独立本地实例中，通过页面点击“新增站点”，填写 `UI-empty-site`、监听地址 `127.0.0.1`、端口 `21609`，点击保存。页面显示“保存成功”，随后内容区白屏。刷新仍会白屏；这会阻止用户继续通过 UI 添加第一条子规则。选择一个没有规则的现有站点也有同样风险。

建议：后端空规则保持 `[]`；前端载入时归一化规则数组并为模板提供安全默认值。补充覆盖真实 API 响应 `rules:null` 和“创建站点 → 添加首条规则”的回归。现有 `WebService.test.js:24` 固定提供 `rules: []`，因此没有覆盖此问题。

证据：[保存前截图](../output/playwright/rp-review-20261015/new-site-before-save.png)、[保存后白屏](../output/playwright/rp-review-20261015/new-site-after-save.png)、[浏览器错误](../output/playwright/rp-review-20261015/browser-console.log)、[保存后页面快照](../output/playwright/rp-review-20261015/after-create.txt)。

## F2：日志流没有持续执行会话撤销检查

位置：`internal/logcenter/api.go:58`、`internal/logcenter/api.go:67`；可复用 `internal/api/auth_state.go` 的 `CurrentSession`。

SSE 仅在进入接口时经过 `requireAuth`。之后循环持续发送日志，既没有复查会话，也没有在注销或全局撤销时取消连接。该接口还清除了服务级写期限，因此有效连接没有固定终止时间。

本地复现顺序：以有效 Cookie 建立日志流，调用退出登录，旧 Cookie 请求 `/api/me` 已返回 401；随后用独立请求生成新的登录事件，旧日志流仍收到“管理员登录成功”。这意味着持有旧连接的一方可以在注销后继续观察后续运行和安全日志。改密或恢复备份后的全局撤销也没有在这个循环中被消费；该扩展影响来自源码分析。

建议：撤销会话时主动取消对应流；每次推送和心跳时复查会话，并为每次写操作设置短写期限，避免慢客户端永久占用有限订阅名额。后者属于源码风险，未进行慢消费者资源耗尽测试。

证据：[实际返回与新日志](../output/playwright/rp-review-20261015/repro-sse.txt)。对照验证：慢请求体期间撤销会话后，普通 JSON 创建站点请求正确返回 401，说明 JSON 解码路径已有保护，[对照结果](../output/playwright/rp-review-20261015/repro-pending-control.txt)。

## F3：初始密码仍属于 LuCI 只读权限

位置：`package/openwrt/luci/usr/share/rpcd/acl.d/luci-app-andeyproxy.json:14`。

当前 ACL 已取消旧版的只读 `file.exec` 权限，这是改进。但 `read.file` 仍包含 `/etc/andey-proxy/initial-password`，并允许 ubus `file.read`。获得这个插件只读权限的 rpcd 账号，在全新安装且管理员尚未改密时，可以读到完整初始管理员密码。强制改密机制允许持有初始密码的人自行设置新密码，不能区分真正管理员。

影响前提明确：存在被授予该插件只读权限的非管理员账号，且初始密码文件仍存在。管理员改密后文件会删除，已完成初始化的设备不受此文件读取路径影响。ACL 的说明文字已承认此授权，但默认边界仍不符合只读账号的权限预期。

建议：从 read 角色移除此文件，将初始化密码领取限制到明确管理员权限或设备本机。验证应包括真实 rpcd 只读账号，不能只检查 Unix 0600 权限。本轮未连接路由器验证实际 rpcd 角色配置。

## F4：配置恢复的部分失败被 UI 显示为成功

位置：`internal/api/backup.go:126`、`web/src/components/SystemMaintenance.vue:320`。

后端返回 `data.warnings`，用于告知配置已落盘但服务没有按新配置生效。前端没有接收响应值，而是直接提示恢复成功并在 1.5 秒后转到登录页，丢失了恢复后是否可用的重要信息。

本地使用只含测试站点的加密备份，先删除该站点，再占用它的 `127.0.0.1:21607` 监听端口，随后恢复备份。接口返回 HTTP 200、`code:0`，同时给出 `Web 服务未按新配置生效: ... bind: address already in use`。这是设计允许的部分成功，必须在 UI 展示。

建议：区分“完整恢复”和“配置已恢复、部分服务未生效”，持续展示各条告警，并提供重新登录和查看服务状态入口。应在跳转前保存或可靠转交告警。

证据：[真实恢复响应](../output/playwright/rp-review-20261015/repro-restore.txt)。本轮未在浏览器提交第二次恢复；前端忽略告警由当前源码直接确认。

## F5：大包上传的超时策略仍不一致

位置：`internal/api/router.go` 的 `requestBudget`、`main.go:238`、`web/src/components/SystemMaintenance.vue:222`。

更新包上传读取期限为 10 分钟，但 Axios 上传请求在 120 秒超时，管理 HTTP 服务也设置了 `WriteTimeout:120s`。仅延长读取期限，无法保证慢链路上传后还能返回验签结果。举例：50 MiB 包在 2 Mbit/s 上行链路中理论传输约 210 秒，超过当前页面超时。

另外，备份恢复的路由读取预算也是 10 分钟，但 UI 请求仅等待 30 秒。超时后用户可能看到失败，而后端恢复已经完成，形成结果不确定性。

建议：为上传设置一致的传输和响应期限；在需要时使用请求级写期限覆盖全局默认值。前端区分上传与后续处理，显示进度并允许查询操作结果。恢复这类改变认证状态的操作尤其需要明确最终结果。

证据级别：源码确认，不将上述时间推算当作限速网络实测；本轮未执行超过 120 秒的真实包上传，也未安装任何更新。

## F6：首屏资源缺少压缩

位置：`internal/adminweb/adminweb.go:43`；现有带哈希资源的长期缓存策略正确。

直接请求内嵌资源，即使发送 `Accept-Encoding: gzip, br`，响应也没有 `Content-Encoding`。浏览器通过 CDP 禁用缓存后载入概览，35 个 assets 资源合计内容 998,467 字节，传输 1,008,967 字节，编码前后体积相同。此测量针对程序直连端口；如果部署前置代理已经压缩，实际影响会减小。

| 资源 | 当前字节 | 本地 gzip 字节 | 可减少 |
|---|---:|---:|---:|
| 入口 CSS | 229,924 | 31,316 | 86.4% |
| locales JS | 155,067 | 42,933 | 72.3% |
| Vue JS | 110,054 | 42,815 | 61.1% |

建议：构建期生成 gzip/Brotli 副本，按客户端支持返回预压缩资源，正确设置 `Content-Encoding`、`Vary` 和缓存头，兼顾 Range/条件请求。构建期压缩可避免小型路由器逐请求压缩的 CPU 开销。

证据：[响应头](../output/playwright/rp-review-20261015/asset-headers.txt)、[冷加载测量](../output/playwright/rp-review-20261015/cold-assets.txt)。本机回环 FCP 数值不代表移动网络体验，本报告不据此给性能评分。

## F7：移动端顶部点击区域偏窄

位置：`web/src/layout/Layout.vue:12`、`web/src/layout/Layout.vue:679`、`web/src/styles/theme.css:305`。

390px 宽度实测：导航按钮 32×44px、刷新按钮 32×44px、语言按钮 26×44px。当前样式只设置最小高度，没有保证最小宽度。建议将这些区域扩展到至少 44×44px，并保留图标的现有视觉尺寸，减少单手操作误触。

这是移动可用性改进，不将“未达到 44px”直接等同于 WCAG 失败。
